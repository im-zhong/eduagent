# Quiz Database Schema Design

## Overview

This document describes the technical decision for the quiz database schema, supporting multiple quiz sources (extracted from textbooks, generated by AI, user-created, etc.).

## Design Choice: Unified Quiz Table + Reference Association Table

### Rationale

We chose to use a unified `quiz` table with a separate `quiz_reference` association table rather than separate tables for each source type.

### Schema

```python
from sqlalchemy import DateTime, ForeignKey, Integer, String, Text
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from datetime import datetime
from typing import Literal


class Quiz(Base):
    """Unified quiz table for all quiz sources."""
    __tablename__ = "quiz"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    doc_id: Mapped[int] = mapped_column(
        Integer,
        ForeignKey("source_document.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )
    source: Mapped[Literal["extracted", "generated", "user_created"]] = mapped_column(
        String(20), nullable=False
    )
    question_json: Mapped[str] = mapped_column(Text, nullable=False)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=datetime.utcnow,
        nullable=False,
    )


class QuizReference(Base):
    """Reference text association for RAG-sourced quizzes."""
    __tablename__ = "quiz_reference"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    quiz_id: Mapped[int] = mapped_column(
        Integer,
        ForeignKey("quiz.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )
    reference_text: Mapped[str] = mapped_column(Text, nullable=False)
    chunk_index: Mapped[int | None] = mapped_column(Integer, nullable=True)
```

### Pros

1. **Single Source of Truth**: All quizzes are in one table, easy to query
2. **Consistent API**: Single endpoint `GET /api/v1/quiz?doc_id=X` returns all questions
3. **Flexible Reference**: Association table handles:
   - Multiple chunks per quiz
   - No reference (e.g., user-created questions)
   - Tracked chunk indices
4. **Future-Proof**: Easy to add new sources (`ai_revised`, `imported`, etc.) without schema changes
5. **Clean UI Display**: Same format regardless of source

### Cons

1. `source` enum needs updates when adding new source types
2. Question JSON structure must be validated per source type

### Usage Examples

```python
# Generate a quiz with RAG references
quiz = Quiz(doc_id=123, source="generated", question_json="{...}")
session.add(quiz)
session.flush()

ref1 = QuizReference(quiz_id=quiz.id, reference_text="chunk 1 text", chunk_index=0)
ref2 = QuizReference(quiz_id=quiz.id, reference_text="chunk 2 text", chunk_index=1)
session.add_all([ref1, ref2])
session.commit()

# Query all quizzes for a document
result = await session.execute(
    select(Quiz).where(Quiz.doc_id == 123)
)
quizzes = result.scalars().all()

# Query a quiz with its references
quiz_with_refs = await session.execute(
    select(Quiz, QuizReference)
    .join(QuizReference)
    .where(Quiz.id == quiz_id)
)
```

## Alternative Considered: Separate Tables

### Schema (Rejected)

```python
class ExtractedQuiz(Base):
    """Quizzes extracted from textbooks."""
    __tablename__ = "extracted_quiz"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    doc_id: Mapped[int] = mapped_column(ForeignKey("source_document.id"))
    question_json: Mapped[str] = mapped_column(Text)
    page_number: Mapped[int]  # Source-specific field

class GeneratedQuiz(Base):
    """AI-generated quizzes."""
    __tablename__ = "generated_quiz"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    doc_id: Mapped[int] = mapped_column(ForeignKey("source_document.id"))
    question_json: Mapped[str] = mapped_column(Text)
    reference_text: Mapped[str]  # Source-specific field
```

### Why Rejected

1. **Duplicate Schema**: Same fields duplicated across tables
2. **Complex Queries**: Need UNION or multiple queries for "all questions"
3. **Migration Overhead**: Adding new sources requires new table
4. **API Complexity**: Multiple endpoints or complex response handling
